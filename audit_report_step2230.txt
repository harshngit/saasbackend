# Backend Sorting — Verification-Only Audit Report

**Audit Type**: Read-Only Architecture & Implementation Verification  
**Audit Scope**: All server-side listing, filtering, and pagination endpoints across the SaaS CRM/ERP backend  
**Repository State**: `main` (Verified against current source code, models, schemas, and queries)

---

## Executive Summary

1. **44 server-side paginated routes** (spanning 42 distinct handlers) were inspected across the entire application.
2. **0 standard CRUD/business listing endpoints** currently accept or support `sort_by` or `sort_order` parameters. All standard listing queries currently use hardcoded SQL `order_by` clauses.
3. **1 endpoint (`GET /reports/{report_type}`)** accepts `sort_by` and `sort_order`, but:
   - It only applies sorting for `gst-summary` in transaction mode.
   - It performs in-memory Python sorting (`rows.sort(...)`) after building records, rather than database-level sorting.
   - All other 16 reports are structured aggregation / financial statements (Profit & Loss, Balance Sheet, Cash Flow, Statement of P&L, Notes to P&L) and are **Out of Scope** per explicit instructions.
4. **1 endpoint (`GET /accounts-payable`)** applies SQL ordering (`SupplierInvoice.supplier_invoice_date.asc(), SupplierInvoice.id.asc()`), but fetches all open invoices with `.all()`, computes aging summaries in Python, and slices the page in memory.
5. **1 endpoint (`GET /warehouses/stock`)** exhibits hybrid pagination: when `low_stock_only=False`, it paginates `Product` in SQL and expands variants in Python; when `low_stock_only=True`, it loads all products, calculates stock positions in Python, and slices in memory.
6. **2 endpoints currently lack stable secondary tie-breaking ordering (`Model.id`)**:
   - `GET /purchase-returns`: orders solely by `PurchaseReturn.created_at.desc()`.
   - `GET /supplier-payments`: orders solely by `SupplierPayment.paid_on.desc(), SupplierPayment.created_at.desc()`.
