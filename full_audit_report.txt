# Backend Sorting — Verification-Only Audit Report

**Audit Type**: Read-Only Architecture & Implementation Verification  
**Audit Scope**: All server-side listing, filtering, and pagination endpoints across the SaaS CRM/ERP backend  
**Repository State**: `main` (Verified against current source code, models, schemas, and queries)

---

## Executive Summary

1. **44 server-side paginated routes** (spanning 42 distinct handlers) were inspected across the entire application.
2. **0 standard CRUD/business listing endpoints** currently accept or support `sort_by` or `sort_order` parameters. All standard listing queries currently use hardcoded SQL `order_by` clauses.
3. **1 endpoint (`GET /reports/{report_type}`)** accepts `sort_by` and `sort_order`, but:
   - It only applies sorting for `gst-summary` in transaction mode.
   - It performs in-memory Python sorting (`rows.sort(...)`) after building records, rather than database-level sorting.
   - All other 16 reports are structured aggregation / financial statements (Profit & Loss, Balance Sheet, Cash Flow, Statement of P&L, Notes to P&L) and are **Out of Scope** per explicit instructions.
4. **1 endpoint (`GET /accounts-payable`)** applies SQL ordering (`SupplierInvoice.supplier_invoice_date.asc(), SupplierInvoice.id.asc()`), but fetches all open invoices with `.all()`, computes aging summaries in Python, and slices the page in memory.
5. **1 endpoint (`GET /warehouses/stock`)** exhibits hybrid pagination: when `low_stock_only=False`, it paginates `Product` in SQL and expands variants in Python; when `low_stock_only=True`, it loads all products, calculates stock positions in Python, and slices in memory.
6. **2 endpoints currently lack stable secondary tie-breaking ordering (`Model.id`)**:
   - `GET /purchase-returns`: orders solely by `PurchaseReturn.created_at.desc()`.
   - `GET /supplier-payments`: orders solely by `SupplierPayment.paid_on.desc(), SupplierPayment.created_at.desc()`.

---

## 1. Classification of All Inspected Endpoints

| Category | Count | Description |
| :--- | :---: | :--- |
| **Already Supported** | **0** | No standard listing endpoint currently supports correct, dynamic database-level `sort_by` / `sort_order`. |
| **Missing Sorting** | **39** | Standard server-side paginated listing endpoints returning `PaginatedResponse[T]` that filter in SQL, apply hardcoded SQL `order_by`, and paginate via SQL `LIMIT`/`OFFSET`, but lack dynamic `sort_by` and `sort_order` parameters. |
| **Incorrect / Incomplete Sorting** | **2** | `GET /accounts-payable` (in-memory slicing after SQL fetch) and `GET /warehouses/stock` (hybrid SQL/in-memory variant expansion). |
| **Out of Scope** | **3** | `GET /reports/{report_type}` (screen) and `GET /reports/{report_type}/export` (export) — structured financial/operational reports protected from general table sorting; and unpaginated collection endpoints. |

## 3. Query Execution Order & Determinism Analysis

All standard listing endpoints in the codebase currently follow this execution flow:
```
1. Base Query: db.query(Model).filter(Model.organization_id == org_id)
2. Filters: Apply where clauses (search, status, date_from, date_to, etc.)
3. Hardcoded Order By: query.order_by(PrimaryColumn.desc(), Model.id.desc())
4. Pagination: paginate(query, page, page_size) -> applies order_by(None).count() then offset().limit().all()
```

### Required Implementation Architecture for Dynamic Sorting:
When dynamic sorting is added to any confirmed endpoint, the SQL execution order must be:
```
1. search/filter (SQL WHERE clauses with tenant isolation preserved)
2. sort (Dynamic validated field .asc() or .desc() from whitelist)
3. stable secondary sort (Model.id.desc() or Model.id.asc() tie-breaker)
4. pagination (SQL COUNT -> SQL OFFSET -> SQL LIMIT)
```

**Tie-Breaking Rule**: When sorting by non-unique columns (e.g. `status`, `category`, `due_date`, `created_at`), multiple rows can have identical sort values. Without a secondary unique ordering (`Model.id`), SQL engines produce non-deterministic row sequences across pages, causing duplicate or skipped rows. Every dynamic sort must be followed by `Model.id.desc()` or `Model.id.asc()`.

## 4. Security, Tenant-Isolation, and Compatibility Risks

1. **SQL Injection & Attribute Exploitation Prevention**:
   - `sort_by` must NEVER be resolved dynamically via `getattr(Model, sort_by)` without an explicit, hardcoded whitelist dictionary:
     ```python
     SORTABLE_FIELDS = {
         "created_at": Model.created_at,
         "name": Model.name,
     }
     ```
   - Attempting to pass unknown or non-whitelisted attributes must raise `HTTP 400 Bad Request` or `HTTP 422 Unprocessable Entity` with a clear message: `"Invalid sort_by '{sort_by}'. Allowed: [...]"`.
2. **Order Direction Validation**:
   - `sort_order` must accept only `"asc"` or `"desc"` (case-insensitive). Any other value must raise `HTTP 400 Bad Request` (`"sort_order must be 'asc' or 'desc'"`). Default to `"desc"` or `"asc"` depending on the entity's natural default.
3. **Tenant Isolation Invariance**:
   - Organization scoping (`Model.organization_id == org_id`) must remain the first and unconditional filter in SQLAlchemy, unaffected by any sorting parameters.
4. **Backward Compatibility**:
   - When `sort_by` is omitted or `None`, the endpoint must fall back to its exact pre-existing default ordering.
   - The response schema `PaginatedResponse[T]` (`items`, `total`, `page`, `page_size`, `total_pages`) must remain unchanged so existing frontend consumers do not break.
